AThe problem

A soft robot has no joints to read

A soft continuum robot bends along its whole length, so there are no joint angles to measure. To train a control model for it, its shape has to be measured from outside, accurately and at a high frame rate.

The robot is about 300 mm tall: four PLA disks spaced roughly 70 mm apart on a flexible backbone, each carrying retroreflective stickers around its rim. Three stepper motors bend it by winding tendons onto spools in the base, controlled from an ESP32 with DRV8825 drivers. The rig around it is a 500 mm aluminium cube with a camera on each corner at a different height, each fitted with a 24-LED infrared ring and an IR-pass filter so the markers light up and the background stays dark.

BHow it works

From raw USB frames to a fitted robot shape

Each stage is its own module with its own command-line tool, and every tool is also a button in the desktop app.

  1. Capture

    v4l2.py · rig.py

    Direct V4L2 memory-mapped capture through ctypes, with no extra dependencies. Every frame carries the kernel's start-of-exposure timestamp and a sequence number. One thread polls all four cameras and applies exposure and gain with read-back and retry.

  2. Clock model

    clock.py

    USB scheduling makes raw timestamps jitter by ±2 ms, so a 13.7 ms gap does not mean a frame was lost. Each camera gets a linear clock fit that locks only after a validated 32-frame window (residuals under 3 ms, period within 3% of nominal). Lost frames are then counted exactly.

  3. Synchronize

    sync.py

    Frames are grouped against a reference camera. Picking the nearest frame leaves up to half a frame of skew (about 4.2 ms); interpolating each camera to a common time brings it under 1 ms.

  4. Calibrate

    calibrate.py · calib.py

    A guided ChArUco routine calibrates each lens, then the camera positions, refined by bundle adjustment. The board lying flat in the first capture defines a z-up world frame, and a triangulated check reports the board's corner spacing error in millimetres.

  5. Detect markers

    markers.py · mask.py

    Thresholding, blob filtering and intensity-weighted sub-pixel centroids. A static mask removes reflections from the cube's rails and the opposite cameras' IR rings, which the diagonal cameras look straight into.

  6. Fit the robot

    model.py · track.py

    A model of four constant-curvature segments is fitted directly to the 2D detections in every camera. Projected markers are matched to detections with Hungarian assignment (gated at 25 px), and the curvatures are solved by robust least squares, so a marker seen by only one camera still counts.

DTiming

Four cameras, four clocks

The cameras are free-running: each one ticks on its own crystal, and the crystals drift 2 to 95 parts per million apart as they warm up. The offset between cameras comes from that drift, not from cable length or hubs. So instead of trying to trigger them together, the software models each clock and interpolates every camera to the same instant.

EProblems solved

What the hardware got wrong, and how it was handled

Four cameras, one serial number

All four cameras report serial 5423534724, and their /dev/video numbers change on every replug. Cameras are identified by USB port path instead, and an assign tool names them by asking you to cover each lens in turn.

USB bandwidth

At 120 fps each camera reserves about 16 MB/s of isochronous bandwidth, so only two can share a 480 Mbit/s link. That set the port layout. A USB-C dock that produced corrupt frames was ruled out.

Dropped frames traced to a cable

Two ports started losing frames after one or two minutes, and the loss kept growing. A soak-test tool exposed the pattern; replacing the cable fixed it, confirmed by a two-hour stream with zero drops. Short tests had missed it, so soak tests now run 3 to 10 minutes.

Heat

The cameras lose frames as they warm up at 120 fps. Ventilation cut the drops, and a 60 fps mode halves the CPU load and keeps them cooler for slower motions.

A mono sensor sending colour

The sensor is monochrome but sends YUV422 MJPEG with empty chroma, so frames are decoded straight to grayscale and no time is spent on colour.

Exposure and motion blur

Auto exposure can quietly lower the frame rate, so exposure is always set by hand. Marker auto-exposure ignores masked pixels and is capped at 2 ms to keep moving markers sharp.

FTooling

Built to be run by someone other than its author

The rig is operated from a GTK desktop app with a button for every step, and each step also works from the terminal.

  • Live dashboard. Per-camera frame rate, frame loss, sync offset, focus aid, exposure tools and histograms.
  • Preflight check. A 35-second test before each session that ends in PASS, WARN or FAIL.
  • Soak test. Long stability runs with per-minute loss graphs, to catch heat and cable faults.
  • Guided calibration. Automatic capture when the board is still, with a coverage map per camera.
  • Record and replay. Raw MJPEG plus timestamps, so tracking can be developed offline.
  • Motor control. ESP32 firmware for three stepper drivers, with a serial console and a Python API.
